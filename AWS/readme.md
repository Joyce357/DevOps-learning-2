**Deployment Models in Cloud Computing**

`What is a deployment Model ?`

A deployment model in cloud computing refers to the specific configuration and arrangement of cloud resources and services that an organization uses to deliver its applications and services. It defines how the cloud infrastructure is set up, who has access to it, and how it is managed. The choice of deployment model depends on factors such as `security requirements, compliance needs, budget constraints, and the level of control desired by the organization`.


`Public Cloud` :

The public cloud is a deployment model in which cloud computing services are delivered over the internet by third-party providers. These services, such as computing power, storage, and applications, are shared among multiple users (known as "tenants") and are accessible to the general public.The provider owns, manages, and assumes all responsibility for the data centers and infrastructure. Examples include `Amazon Web Services (AWS),` `Microsoft Azure`, and `Google Cloud Platform (GCP)`.

`Private Cloud`

The private cloud is a cloud deployment model in which computing resources are used exclusively by a single organization. These resources can be hosted on-premises (within the organization's data center) or by a third-party provider but remain dedicated solely to that organization, ensuring greater control, privacy, and security.

`Hybrid Cloud`

The hybrid cloud is a cloud computing model that combines the use of both public and private cloud environments, allowing data and applications to be shared between them. This approach enables businesses to leverage the scalability and cost-efficiency of public cloud services while maintaining the security and control of private cloud infrastructure.




**SERVICE MODELS**

`What is a service model ?`
A service model in cloud computing refers to the specific type of service that a cloud provider offers to   
users. It defines the level of abstraction and control that users have over the underlying infrastructure and resources. The three primary service models in cloud computing are `Infrastructure as a Service (IaaS)`, `Platform as a Service (PaaS)`, and  `Software as a Service (SaaS)`.

1. `Infrastructure as a Service (Iaas)`

Infrastructure as a Service (IaaS) is a cloud computing service model that provides virtualized computing resources over the internet. In this model, users can rent or lease virtual machines, storage, and networking resources from a cloud provider on a pay-as-you-go basis. IaaS allows users to have control over the operating systems, applications, and data while the cloud provider manages the underlying infrastructure.

2. `Platform as a Service (PaaS)`
Platform as a Service (PaaS) is a cloud computing service model that provides a platform for developers to build, deploy, and manage applications without worrying about the underlying infrastructure. PaaS offers a complete development environment, including tools, libraries, and runtime environments, allowing developers to focus on coding and application logic rather than infrastructure management.

3. `Software as a Service (SaaS)`

Software as a Service (SaaS) is a cloud computing service model that delivers software applications over the internet on a subscription basis. In this model, users can access and use software applications hosted by a cloud provider without needing to install or maintain them on their local devices. SaaS applications are typically accessed through web browsers, and the cloud provider is responsible for managing the infrastructure, security, and updates of the software.

**What is a Region**

In Amazon Web Services (AWS), a region is a geographical area where AWS has multiple data centers (availability zones). Each region is designed to be completely isolated from other regions to ensure fault tolerance and stability. AWS operates multiple regions globally, and each region consists of multiple availability zones.

+ Each region is identified by a unique name (e.g., us-east-1, eu-west-1 , ca-central-1 ).
+ Regions are composed of multiple availability zones (data centres).
+ AWS services are typically deployed globally across multiple regions to provide redundancy and improve performance for users located in different geographic locations.



**WHAT IS AN AVAILABILITY ZONE (AZ)**

An availability zone (AZ) is one or more discrete data centers within a region. These availability zones are interconnected through low-latency links, but they are physically separated from each other. This physical separation is important for providing redundancy and resilience. If one availability zone within a region experiences a failure, the other availability zones in the same region can continue to operate independently, ensuring high availability and fault tolerance for applications and services hosted on AWS.

+ Availability zones are isolated from each other to minimize the impact of failures and improve fault tolerance.
+ They are connected through high-speed, low-latency links to enable synchronous replication and data transfer between availability zones.
+ Deploying applications across multiple availability zones within a region enhances fault tolerance and high availability by ensuring that failures in one availability zone do not impact the availability of applications hosted in other availability zones.


**Why did AWS Introduce Multi Availability Zones ? (AZ)** 

+ `Disaster Recovery` : 

Availability zones facilitate disaster recovery by providing geographically separated infrastructure within the same region. Organizations can use availability zones to replicate data and resources across different zones, enabling them to quickly recover from disasters or regional outages without data loss or downtime.

+ `Improved Perfomance` :

Availability zones are interconnected through low-latency links within the same region. This allows for synchronous data replication and enables applications to achieve low-latency communication between components deployed across different availability zones, enhancing overall performance.

+ `High Availability`:

Applications deployed across multiple availability zones can achieve higher levels of availability because they are not dependent on a single data center or infrastructure. Even if one availability zone becomes unavailable due to maintenance, hardware failures, or other issues, the application can remain accessible from other availability zones.

+ `Fault Tolerance`

By distributing resources across multiple availability zones within the same region, applications can withstand failures in one availability zone without impacting availability. This redundancy ensures that if one availability zone experiences an outage, services can continue to operate from other availability zones.

+ `Data Redundancy`
Availability zones enable data redundancy by allowing organizations to replicate data across multiple zones within the same region. This ensures that even if one availability zone experiences a failure, the data remains intact and accessible from other availability zones, reducing the risk of data loss.

+ `Scalability and Flexibility`

Availability zones provide scalability by allowing organizations to distribute workloads across multiple zones within a region. As demand for resources grows, organizations can easily scale their applications horizontally by adding more instances or services across different availability zones

+ `Compliance and Data residency `

Some regulatory requirements mandate data residency within specific geographic regions. Availability zones allow organizations / companies to ensure compliance with these requirements by deploying resources in designated regions while still benefiting from the redundancy and fault tolerance provided by multiple availability zones.

An IAM policy in AWS Identity and Access Management (IAM) is a JSON document that defines permissions for an IAM user, group, or role. Apart from managed policies where we have (customer and aws managed policies) we also have an Inline Policy a user can create

**Inline Policy**

An inline policy is a type of IAM policy that is directly embedded within a specific IAM user, group, or role. Unlike managed policies, which are standalone and can be attached to multiple entities, inline policies are unique to the entity they are associated with and cannot be reused across different users, groups, or roles.
+ This is a policy created by the iam user and managed by the user
+ Unlike Managed Policies (standalone + reusable), inline policies are one-to-one with the entity (user , group or iam role).
+ If you delete the user/group/role, the inline policy goes too.
+ Not reusable: Cannot be shared with another identity.
+ Good for exceptions: Special permissions unique to one user/role.


`When to use an Inline Policy ?`

+ When you have a specific use case that requires permissions that are unique to a single user, group, or role and are not applicable to other entities.
+ When you want to ensure that the permissions defined in the policy are tightly coupled with the specific user, group, or role and should not be reused or shared across multiple entities.
+ When you want to create a policy that is only relevant to a specific user, group, or role and does not need to be maintained or updated independently of that entity.
+ When you have a temporary or one-time permission requirement that does not warrant the creation of a reusable managed policy.

+ `Effect`: Specifies whether the statement allows or denies access. In this example, both statements have an "Allow" effect, meaning they grant permissions.
+ `Action`: Lists the specific actions that are allowed or denied. In this example, the first statement allows actions related to starting and stopping EC2 instances, while the second statement allows actions related to describing EC2 resources.Action simply defines what the user can do 
+ `Resource`: Specifies the AWS resources to which the actions apply. In this example, the resource is set to "*", which means the permissions apply to all resources . You can specify specific ARNs (Amazon Resource Names) to limit the permissions to certain resources if you wish . 

+ `Condition` :  

This is an optional element that allows you to specify conditions under which the policy statement applies. Conditions can be based on factors such as the time of day, the source IP address, or the presence of specific tags on resources. In our example policy, there are no conditions specified. Conditions in IAM policies let you apply extra restrictions beyond just the Action and Resource. Think of them as “if clauses” that narrow when permissions apply (based on tags, IP addresses, time, MFA, encryption, etc.).

**What is MFA ?**:

MFA stands for Multi-Factor Authentication. It is a security mechanism that requires users to provide two or more forms of authentication to verify their identity when accessing a system or service. In the context of AWS,  `MFA adds an extra layer of security` to your AWS account by requiring users to provide a second form of authentication (in addition to their password) when signing in to the AWS Management Console or making API calls. This helps protect your account from unauthorized access, even if a user's password is compromised.

Saving Plans provide the same discounts as `Reserved Instances` but with more flexibility, allowing you to switch between `instance types`, `regions`, and even AWS services while still benefiting from the discounted rates.

With the saving plans it offers lower price on EC2 instances regardless of the instance family (instance type) , size , OS , tenancy , aws region in exhange the above commitment of usage.

`Note` : Instead of committing to a specific instance (like Reserved Instances), you commit to a dollar amount of usage per hour.

5. `DEDICATED HOST`: 

A Dedicated Host is a physical server with EC2 instance capacity fully dedicated to your use. This option is ideal for applications that require a high level of isolation, compliance, or licensing requirements that cannot be met with shared infrastructure. With Dedicated Hosts, you have more control over the placement of your instances and can use your existing server-bound software licenses.

Use Case : scenario where you what EC2 instances to be physically isolated at the host hardware level from instances that belong to other AWS accounts.When a company is subject meet certain policies or regulatory .

`Pricing` : varies based on instance family , region and payment option you choose . You can pay to own the entire host , its expensive whereas dedicated instances which are cost effective

`Why Use Dedicated Hosts?`

+ `Licensing`: Lets you use existing server-bound software licenses (Windows Server, SQL Server, Oracle) tied to sockets, cores, or physical servers.
+ You can see the physical sockets, cores, and host IDs for tracking.


6. `DEDICATED INSTANCE` : 

A Dedicated Instance is an EC2 instance that runs on hardware dedicated to a single customer. `Unlike Dedicated Hosts, you do not have control over the physical server`, but your instances are still isolated at the `hardware level` from instances of other customers. Dedicated Instances are ideal for applications that require a high level of isolation but do not have specific compliance or licensing requirements that necessitate a Dedicated Host.

**Advantages of Dedicated Instance:**

+ `Isolation`: Runs on hardware that is dedicated to a single customer, providing a higher level of isolation compared to shared instances.
+ `Cost-effective`: Generally more affordable than Dedicated Hosts while still providing hardware-level isolation.
+ `No need for host management`: You do not have to manage the underlying physical server,as AWS handles the infrastructure, allowing you to focus on your applications.
+ `Ideal for applications with isolation needs`: Suitable for applications that require isolation but do not have specific compliance or licensing requirements that necessitate a Dedicated Host.


**Disadvantages of Dedicated Instance:**
+ `Less control`: You do not have control over the physical server, which may not meet certain compliance or licensing requirements.
+ `Higher cost than shared instances`: Dedicated Instances are more expensive than standard On-Demand instances

**AMI = Amazon Machine Image**

`What is an AMI ?` ; 

An Amazon Machine Image (AMI) is a `pre-configured` template that contains the necessary information to launch an EC2 instance. It includes the operating system or  application server, or  applications required to run your instance. AMIs can be created from existing instances or provided by AWS as standard images for various operating systems and software configurations. 

`AMI includes :` 

+ An operating system (e.g., Linux, Windows)
+ Application server (e.g., Apache, Nginx , git )
+ Applications (e.g., WordPress, MySQL)
+ Custom Configurations ( security agents , monitoring tools etc )


**WHAT YOU SHOULD KNOW WHEN IT COMES TO AMI** 

+ Template for your ec2 instance. This is the Pre-configured OS or application for your virtual machine
+ You can use AWS provided AMIs or create your own custom AMIs.
+ Users can customize AMI to match their specific needs and they can also modify existing AMI
+ AMIs are region-specific, so you need to ensure that you are using the correct AMI for the region where you want to launch your EC2 instance.
+ You can use a single AMI to create multiple ec2- instances with the same AMI configurations
+ AMIs can be shared with other AWS accounts, allowing you to collaborate and share resources across accounts.
+ There are Private AMI (only the user who owns it can see and use it ) and Public AMI (anyone on the internet (aws) can see and use it)
+ You can also use AWS Marketplace to find and purchase AMIs that are pre-configured with specific software or applications.
+ AMI can be build from a snapshoot
+ AMI can be used to create an Auto Scaling group, which allows you to automatically launch and terminate EC2 instances based on demand.


**TYPES OF AMI**


+ `AWS Marketplace AMIs`: These are pre-configured AMIs provided by AWS and its partners, available in the AWS Marketplace. They include a wide range of software and applications, such as operating systems, databases, and development tools.

+ `Custom AMIs`: These are AMIs that you create yourself, based on your specific requirements. You can customize the operating system, applications, and configurations to meet your needs.

+ `Community AMIs`: These are AMIs that are shared by other AWS users. They can be public or private, and they may include a variety of configurations and software.

+ `AWS-provided AMIs`: These are basic AMIs provided by AWS that include popular operating systems like `Amazon Linux, Ubuntu, and Windows Server`. They serve as a starting point for creating custom AMIs.

**Why do companies create their own custom AMI ?** 

+ `Standardization`: Custom AMIs allow companies to create a standardized environment for their applications, ensuring consistency across all instances launched from the AMI.

+ `Faster Deployment`: Launching an instance from a custom AMI is faster than setting up a new instance from scratch, as the AMI already contains the necessary software and configurations.

+ `Cost Efficiency`: By creating a custom AMI, companies can optimize the software and configurations to reduce costs and improve performance.

+ `Security`: Custom AMIs can be configured with specific security settings and software, helping to enhance the security posture of the instances launched from the AMI.

+ `Compliance`: Custom AMIs can be designed to meet specific compliance requirements, ensuring that instances launched from the AMI adhere to necessary regulations and standards.


`What are some of the best practices for AMI` 

+ Regularly update and patch your custom AMIs to ensure they include the latest security updates and software versions.
+ Use descriptive names and tags for your AMIs to make it easier to identify their purpose and contents.
+ Limit access to your custom AMIs to only those who need it, using AWS Identity and
Access Management (IAM) policies.
+ Test your custom AMIs before using them in production to ensure they work as expected and do
not contain any vulnerabilities or misconfigurations.
+ Use versioning for your custom AMIs to keep track of changes and allow for easy rollback (e.g parameterstore)
+ Automate → Use EC2 Image Builder or CI/CD pipelines to refresh AMIs monthly/quarterly.
+ Secure them → Harden OS, remove unused packages, include security agents.


**How to copy an AMI from ONE region in aws to another** 

+ Go to the EC2 dashboard and click on "AMIs" in the left-hand menu.
+ Locate the AMI you want to copy and select it.
+ Click on the "Actions" button and select "Copy AMI" from the dropdown menu
+ In the "Copy AMI" dialog box, select the destination region where you want to copy the AMI.
+ Provide a name and description for the copied AMI, and click on the "Copy AMI" button to start the copying process.
+ Once the copying process is complete, you can go to the destination region and find the copied AMI in the "AMIs" section of the EC2 dashboard.


**What are some of the use cases of An AMI ?**  

+ `Backup and Disaster Recovery`: AMIs can be used to quickly recover from failures by launching new instances from a pre-configured AMI.
+ `Scaling`: AMIs can be used to quickly scale up your infrastructure by launching multiple instances from the same AMI using an auto scaling group in aws 
+ `Testing and Development`: AMIs can be used to create consistent environments for testing and development, allowing developers to quickly spin up instances with the necessary software and configurations.
+ `Custom Software`: AMIs can be used to create instances with custom software and configurations that
are not available in standard AWS-provided AMIs.
+ `Multi-Region Deployments`: AMIs can be copied across regions, allowing you to
deploy applications in multiple regions with the same configuration.
+ `Data migration` moving an ami from one region to another with all the data inside
