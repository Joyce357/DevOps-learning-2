**Deployment Models in Cloud Computing**

`What is a deployment Model ?`

A deployment model in cloud computing refers to the specific configuration and arrangement of cloud resources and services that an organization uses to deliver its applications and services. It defines how the cloud infrastructure is set up, who has access to it, and how it is managed. The choice of deployment model depends on factors such as `security requirements, compliance needs, budget constraints, and the level of control desired by the organization`.


`Public Cloud` :

The public cloud is a deployment model in which cloud computing services are delivered over the internet by third-party providers. These services, such as computing power, storage, and applications, are shared among multiple users (known as "tenants") and are accessible to the general public.The provider owns, manages, and assumes all responsibility for the data centers and infrastructure. Examples include `Amazon Web Services (AWS),` `Microsoft Azure`, and `Google Cloud Platform (GCP)`.

`Private Cloud`

The private cloud is a cloud deployment model in which computing resources are used exclusively by a single organization. These resources can be hosted on-premises (within the organization's data center) or by a third-party provider but remain dedicated solely to that organization, ensuring greater control, privacy, and security.

`Hybrid Cloud`

The hybrid cloud is a cloud computing model that combines the use of both public and private cloud environments, allowing data and applications to be shared between them. This approach enables businesses to leverage the scalability and cost-efficiency of public cloud services while maintaining the security and control of private cloud infrastructure.




**SERVICE MODELS**

`What is a service model ?`
A service model in cloud computing refers to the specific type of service that a cloud provider offers to   
users. It defines the level of abstraction and control that users have over the underlying infrastructure and resources. The three primary service models in cloud computing are `Infrastructure as a Service (IaaS)`, `Platform as a Service (PaaS)`, and  `Software as a Service (SaaS)`.

1. `Infrastructure as a Service (Iaas)`

Infrastructure as a Service (IaaS) is a cloud computing service model that provides virtualized computing resources over the internet. In this model, users can rent or lease virtual machines, storage, and networking resources from a cloud provider on a pay-as-you-go basis. IaaS allows users to have control over the operating systems, applications, and data while the cloud provider manages the underlying infrastructure.

2. `Platform as a Service (PaaS)`
Platform as a Service (PaaS) is a cloud computing service model that provides a platform for developers to build, deploy, and manage applications without worrying about the underlying infrastructure. PaaS offers a complete development environment, including tools, libraries, and runtime environments, allowing developers to focus on coding and application logic rather than infrastructure management.

3. `Software as a Service (SaaS)`

Software as a Service (SaaS) is a cloud computing service model that delivers software applications over the internet on a subscription basis. In this model, users can access and use software applications hosted by a cloud provider without needing to install or maintain them on their local devices. SaaS applications are typically accessed through web browsers, and the cloud provider is responsible for managing the infrastructure, security, and updates of the software.

**What is a Region**

In Amazon Web Services (AWS), a region is a geographical area where AWS has multiple data centers (availability zones). Each region is designed to be completely isolated from other regions to ensure fault tolerance and stability. AWS operates multiple regions globally, and each region consists of multiple availability zones.

+ Each region is identified by a unique name (e.g., us-east-1, eu-west-1 , ca-central-1 ).
+ Regions are composed of multiple availability zones (data centres).
+ AWS services are typically deployed globally across multiple regions to provide redundancy and improve performance for users located in different geographic locations.



**WHAT IS AN AVAILABILITY ZONE (AZ)**

An availability zone (AZ) is one or more discrete data centers within a region. These availability zones are interconnected through low-latency links, but they are physically separated from each other. This physical separation is important for providing redundancy and resilience. If one availability zone within a region experiences a failure, the other availability zones in the same region can continue to operate independently, ensuring high availability and fault tolerance for applications and services hosted on AWS.

+ Availability zones are isolated from each other to minimize the impact of failures and improve fault tolerance.
+ They are connected through high-speed, low-latency links to enable synchronous replication and data transfer between availability zones.
+ Deploying applications across multiple availability zones within a region enhances fault tolerance and high availability by ensuring that failures in one availability zone do not impact the availability of applications hosted in other availability zones.


**Why did AWS Introduce Multi Availability Zones ? (AZ)** 

+ `Disaster Recovery` : 

Availability zones facilitate disaster recovery by providing geographically separated infrastructure within the same region. Organizations can use availability zones to replicate data and resources across different zones, enabling them to quickly recover from disasters or regional outages without data loss or downtime.

+ `Improved Perfomance` :

Availability zones are interconnected through low-latency links within the same region. This allows for synchronous data replication and enables applications to achieve low-latency communication between components deployed across different availability zones, enhancing overall performance.

+ `High Availability`:

Applications deployed across multiple availability zones can achieve higher levels of availability because they are not dependent on a single data center or infrastructure. Even if one availability zone becomes unavailable due to maintenance, hardware failures, or other issues, the application can remain accessible from other availability zones.

+ `Fault Tolerance`

By distributing resources across multiple availability zones within the same region, applications can withstand failures in one availability zone without impacting availability. This redundancy ensures that if one availability zone experiences an outage, services can continue to operate from other availability zones.

+ `Data Redundancy`
Availability zones enable data redundancy by allowing organizations to replicate data across multiple zones within the same region. This ensures that even if one availability zone experiences a failure, the data remains intact and accessible from other availability zones, reducing the risk of data loss.

+ `Scalability and Flexibility`

Availability zones provide scalability by allowing organizations to distribute workloads across multiple zones within a region. As demand for resources grows, organizations can easily scale their applications horizontally by adding more instances or services across different availability zones

+ `Compliance and Data residency `

Some regulatory requirements mandate data residency within specific geographic regions. Availability zones allow organizations / companies to ensure compliance with these requirements by deploying resources in designated regions while still benefiting from the redundancy and fault tolerance provided by multiple availability zones.

An IAM policy in AWS Identity and Access Management (IAM) is a JSON document that defines permissions for an IAM user, group, or role. Apart from managed policies where we have (customer and aws managed policies) we also have an Inline Policy a user can create

**Inline Policy**

An inline policy is a type of IAM policy that is directly embedded within a specific IAM user, group, or role. Unlike managed policies, which are standalone and can be attached to multiple entities, inline policies are unique to the entity they are associated with and cannot be reused across different users, groups, or roles.
+ This is a policy created by the iam user and managed by the user
+ Unlike Managed Policies (standalone + reusable), inline policies are one-to-one with the entity (user , group or iam role).
+ If you delete the user/group/role, the inline policy goes too.
+ Not reusable: Cannot be shared with another identity.
+ Good for exceptions: Special permissions unique to one user/role.


`When to use an Inline Policy ?`

+ When you have a specific use case that requires permissions that are unique to a single user, group, or role and are not applicable to other entities.
+ When you want to ensure that the permissions defined in the policy are tightly coupled with the specific user, group, or role and should not be reused or shared across multiple entities.
+ When you want to create a policy that is only relevant to a specific user, group, or role and does not need to be maintained or updated independently of that entity.
+ When you have a temporary or one-time permission requirement that does not warrant the creation of a reusable managed policy.

+ `Effect`: Specifies whether the statement allows or denies access. In this example, both statements have an "Allow" effect, meaning they grant permissions.
+ `Action`: Lists the specific actions that are allowed or denied. In this example, the first statement allows actions related to starting and stopping EC2 instances, while the second statement allows actions related to describing EC2 resources.Action simply defines what the user can do 
+ `Resource`: Specifies the AWS resources to which the actions apply. In this example, the resource is set to "*", which means the permissions apply to all resources . You can specify specific ARNs (Amazon Resource Names) to limit the permissions to certain resources if you wish . 

+ `Condition` :  

This is an optional element that allows you to specify conditions under which the policy statement applies. Conditions can be based on factors such as the time of day, the source IP address, or the presence of specific tags on resources. In our example policy, there are no conditions specified. Conditions in IAM policies let you apply extra restrictions beyond just the Action and Resource. Think of them as “if clauses” that narrow when permissions apply (based on tags, IP addresses, time, MFA, encryption, etc.).

**What is MFA ?**:

MFA stands for Multi-Factor Authentication. It is a security mechanism that requires users to provide two or more forms of authentication to verify their identity when accessing a system or service. In the context of AWS,  `MFA adds an extra layer of security` to your AWS account by requiring users to provide a second form of authentication (in addition to their password) when signing in to the AWS Management Console or making API calls. This helps protect your account from unauthorized access, even if a user's password is compromised.

**KEY PAIRS** 

`What is a Keypair` : 

A key pair is a set of security credentials that are used to securely connect to an EC2 instance. It consists of a `public key and a private key`. The public key is stored on the EC2 instance, while the private key is kept by the user. When you launch an EC2 instance, you can specify a key pair to associate with the instance, allowing you to securely connect to it using SSH (for Linux instances) or RDP (for Windows instances). Key pairs are essential for ensuring secure access to your EC2 instances and should be managed carefully to prevent `unauthorized access.` 

`Note`; You can create an ec2 instance without a keypair . But you wont be able to login via ssh 

`How Key Pairs Work`
+ When you create a key pair, AWS generates a public key and a private key.
+ The public key is stored on the EC2 instance, while you download and securely store the
private key on your local machine.
+ To connect to the EC2 instance, you use the private key with an SSH client (
Linux) or RDP client (Windows) to authenticate your access.
+ The EC2 instance verifies the private key against the stored public key to grant access.
+ You can select an existing keypair if you have one already (or create) a Key new Pair.
+ You can use a single key pair on multiple ec2 instances 
+ You download the private key file (.pem) to your local machine. ( downloads folder )

`Note :`

+ Keep your private key secure and do not share it with anyone. If someone gains access to your private key, they can potentially access your EC2 instances. 
+ If you lose your private key, you will not be able to access your EC2 instances through ssh , and you will need to create a new key pair and update your instances to use the new public key.
+ An ec2 instance without a keypair you wont be able to SSH into the server but you can still login to the server using different methods
+ When naming a keypair use a single name , do not put spaces in the naming convention
+ When you create a keypair for the first time it goes to your downloads but you like you can move it from there and place in any folder of your choice 
+ If this is the first time you are using the keypair you will need to update the permissions and you need to be in the location where the key is. `chmod 400 <keypair-name>`
+ To login into an EC2 instance through ssh, security group inbound rule port 22 must be open . The common troubleshooting error you will see when its connectivity problems or issues like ports `Operation timed out`: Security group or NACL
+ If you are using windows and want to connect to a linux instance you can use `putty` as an ssh client but putty does not support .pem file so you will need to convert the .pem file to .ppk file using puttygen

**Use Cases of Key Pairs**

+ `Secure Access`: Key pairs provide a secure method for accessing EC2 instances, ensuring that only authorized users can connect to the instances.
+ `Automation`: Key pairs can be used in automation scripts and tools to securely connect to EC2
instances for tasks such as configuration management, deployment, and monitoring.
+ `Multi-User Access`: Key pairs allow multiple users to securely access the same EC2
instance by sharing the public key while keeping their private keys secure.
+ `Compliance`: Key pairs help meet security and compliance requirements by providing a secure authentication method for accessing EC2 instances.
+ `Remote Management`: Key pairs enable remote management of EC2 instances, allowing administrators to perform
maintenance, updates, and troubleshooting tasks without needing physical access to the server.


**What are the methods of logging into an EC2 instance**

+ `SSH (Secure Shell)`: For Linux instances, you can use an SSH client (like OpenSSH or PuTTY) to connect to the instance using the private key from your key pair. 

+ `RDP (Remote Desktop Protocol)`: For Windows instances, you can use an RDP client to connect to the instance using the private key from your key pair to retrieve the administrator password.

+ `EC2 Instance Connect`: This is a browser-based SSH connection method provided by AWS for Linux instances, allowing you to connect to your instance without needing a separate SSH client or key pair.

+ `Session Manager`: This is a feature of AWS Systems Manager that allows you to securely connect to your EC2 instances without needing SSH or RDP. It uses the AWS Management Console or AWS CLI to establish a secure session with the instance.

+ `EC2 Serial Console` : 
This is a feature that provides access to the serial port of your EC2 instances, allowing you to troubleshoot and recover instances that are not responding to SSH or RDP connections. It can be accessed through the AWS Management Console or AWS CLI.


**How To Login into an EC2 using Session Manager** 

+ Ensure that the EC2 instance has the SSM agent installed and running.
+ Attach an IAM role to the EC2 instance with the necessary permissions for Systems Manager (e.g., `AmazonSSMManagedInstanceCore`).
+ Go to the AWS Systems Manager console and navigate to "Session Manager."
+ Click on "Start session" and select the EC2 instance you want to connect to.
+ Click on "Start session" to establish a secure connection to the instance through the browser-based
terminal provided by Session Manager. You can now run commands and manage your EC2 instance without needing SSH or RDP access.


**Most commonly used approach to login into EC2 instances by companies ?**

+ For Linux instances, SSH is the most commonly used method for logging in, as it provides secure and direct access to the instance's command line.

+ For Windows instances, RDP is the most commonly used method for logging in, as it provides a graphical interface for managing the instance.

+ However, with the increasing emphasis on security and automation, many companies are also adopting `Session Manager` for secure and convenient access to their EC2 instances without the need for managing SSH keys or RDP credentials.

+ `Internal Communication`: For instances that need to communicate with each other within a VPC,

+ `Remote Desktop Access`: For a Windows server that requires RDP access, you would allow
inbound traffic on port 3389 from specific IP addresses to ensure secure access.
+ `Custom Applications`: For custom applications, you would allow inbound traffic on the specific ports used by your application (e.g., port 5000 for a Flask application) from trusted sources or security groups.

**Best Practices for Security Groups**

+ Follow the principle of least privilege by only allowing necessary traffic and blocking all other traffic.
+ Regularly review and update your security group rules to ensure they align with your current security requirements.
+ Use specific IP addresses or CIDR blocks instead of allowing traffic from all sources (0.0.0.0/0)
+ Use security group references to allow traffic between instances within the same VPC instead of using IP addresses.
+ Monitor security group usage and changes using AWS CloudTrail and AWS Config to detect any unauthorized modifications
+ Use descriptive names and tags for your security groups to easily identify their purpose and associated instances.

There are two ways we can scale in aws

+ Locate the EBS volume you want to scale and select it.
+ Click on the "Actions" button and select "Modify Volume" from the dropdown menu.
+ In the "Modify Volume" dialog box, specify the new size for the volume and click
on the "Modify" button to start the scaling process.
+ Once the modification process is complete, you may need to extend the file system on the volume
to utilize the new space. This can be done using the appropriate commands for your operating system (e.g., `resize2fs` for Linux or Disk Management for Windows). For linux run the following commands :

`lsblk` : to list the block devices and identify the volume you modified ( e.g /dev/xvdf)

`sudo resize2fs /dev/nvme0n1p1` : to grow the partition on the volume ( e.g xvdf1)

`df -hT` : verify using this command 






**How to Scale an EBS Volume (Horizontal Scaling)**

+ Click on the "Create Volume" button to create a new EBS volume with the desired
size and configuration.
+ Once the new volume is created, select it and click on the "Actions" button,
then select "Attach Volume" from the dropdown menu.
+ In the "Attach Volume" dialog box, select the EC2 instance you want to attach
the volume to and specify the device name (e.g., /dev/sdf) before clicking on the "Attach" button.

e.g., partitioning, formatting, and mounting) to start using the additional storage capacity

**Differences Between Elastic File System (EFS) and EBS volumes***

| Feature              | **Amazon EBS (Elastic Block Store)**                            | **Amazon EFS (Elastic File System)**                       |
|----------------------|-----------------------------------------------------------------|-----------------------------------------------------------|
| **Storage Type**     | Block-level storage (like a virtual hard disk).                 | `File-level` storage using NFS protocol.                    |
| **Accessibility**    | Attached to **one EC2 instance** at a time (per AZ). Multi-Attach only for io1/io2 in same AZ. | Can be mounted by **multiple EC2 instances** across AZs.   |
| **Scalability**      | Manual scaling (up to 64 TiB). Must resize and expand FS.       | Automatically scales up/down with usage (petabyte scale).  |
| **Performance**      | Consistent, low-latency performance. Volume types: gp3, io1/io2, st1, sc1. | Throughput scales with size. Supports bursting & provisioned throughput. |
| **Backup & Recovery**| Point-in-time snapshots stored in S3.                          | Automated backups via AWS Backup. Multi-AZ replication.    |
| **Cost Model**       | Pay for **provisioned size** (even if not fully used).          | Pay for **actual storage used**. Higher cost per GB.       |
| **Best Use Cases**   | Databases, boot volumes, transactional apps.                    | Shared storage, CMS, big data, multi-instance workloads.   |

`What is a Load Balancer ?`: 

A load balancer is a device or software that distributes incoming network traffic across multiple servers (ec2-instances) or resources to ensure optimal performance, reliability, and scalability of applications. It acts as a reverse proxy, receiving client requests(end users , customers ) and forwarding them to the appropriate backend servers (ec2-instances) based on various algorithms and health checks . Load balancers help prevent `server overload`, improve response times, and enhance the overall availability of applications by distributing the workload evenly across multiple servers. They can be used in various scenarios, such as web applications, databases, and microservices architectures, to ensure that resources are utilized efficiently and that users experience consistent performance.

**Benefits of A Load Balancer or Why do companies use a Load Balancer ?**

+ `Improved Performance`: Load balancers distribute incoming traffic across multiple servers, preventing any single server from becoming overwhelmed. This helps to maintain optimal performance and responsiveness of applications, even during high traffic periods. 

+ `High Availability`: Load balancers can detect server failures and automatically redirect traffic to healthy servers, ensuring that applications remain available and accessible to users. This helps to minimize downtime and improve the overall reliability of applications.

+ `Scalability`: Load balancers allow for easy scaling of applications by adding or removing servers from the pool of resources. This enables organizations to handle increased traffic and accommodate growth without disruption to users.

+ `Flexibility`: Load balancers can support various types of applications and protocols, making them suitable for a wide range of use cases. They can be used for web applications, databases, microservices, and more.

+ `Cost Efficiency`: By distributing traffic across multiple servers, load balancers can help to optimize resource utilization and reduce the need for over-provisioning. This can lead to cost savings by allowing organizations to use their resources more efficiently.

+ `Centralized Management`: Load balancers provide a centralized point of control for managing traffic distribution and monitoring the health of backend servers. This allows administrators to easily configure and manage their applications from a single interface.

**What Does different Layers mean in Load Balancing e.g Layer 2 , Layer 3 , Layer 4 etc**

In the context of load balancing, different layers refer to the OSI (Open Systems Interconnection) model, which is a conceptual framework used to understand and implement network protocols in seven layers. Each layer has specific functions and responsibilities in the communication process.

- `Layer 1` : Physical Layer :

This layer is responsible for the physical connection between devices, including the transmission of raw bits over a communication channel. It deals with the hardware aspects of networking, such as cables, switches, and network interface cards.
Key Elements: Electrical signals, cabling, connectors, network interface cards (NICs).

Example: Ethernet cables, fiber optics, physical ports.

- `Layer 2` : Data Link Layer :

Function: Provides node-to-node data transfer and handles error detection and correction from the physical layer.
Key Elements: MAC addresses, switches, frames.
Example: Ethernet, Wi-Fi (802.11), MAC address.
This layer is responsible for the reliable transfer of data frames between devices on the same local network. It handles error detection and correction, as well as flow control. Load balancers that operate at Layer 2 can distribute traffic based on MAC addresses.

- `Layer 3` : Network Layer :
Function: Responsible for routing packets (data or information) across different networks and handling logical addressing (IP addresses).
Key Elements: IP addresses, routers, packets.
Example: IP (Internet Protocol), ICMP (Internet Control Message Protocol).
This layer is responsible for routing packets across different networks and handling logical addressing (IP addresses). Load balancers that operate at Layer 3 can distribute traffic based on IP addresses.

- `Layer 4` : Transport Layer :
Function: Provides end-to-end communication and manages data flow control, error handling, and connection management.
Key Elements: Ports, TCP/UDP protocols, segments/datagrams.
Example: TCP (Transmission Control Protocol), UDP (User Datagram Protocol).
This layer is responsible for providing end-to-end communication and managing data flow control, error handling, and connection management. Load balancers that operate at Layer 4 can distribute traffic based on TCP/UDP ports and protocols.

- `Layer 5` : Session Layer :
Function: Manages sessions or connections between applications. It establishes, maintains, and terminates connections.  
Key Elements: Sessions, dialogues, connections.
Example: NetBIOS, RPC (Remote Procedure Call).
This layer is responsible for managing sessions or connections between applications. It establishes, maintains, and terminates connections. Load balancers that operate at Layer 5 can manage sessions and maintain state information for client connections.

- `Layer 6` : Presentation Layer :
Function:
This layer is responsible for translating data between the application layer and the network. It handles data encryption, compression, and formatting to ensure that data is presented in a way that applications can understand.
Key Elements: Data translation, encryption, compression.
Example: SSL/TLS (Secure Sockets Layer/Transport Layer Security), JPEG, ASCII.

- `Layer 7` : Application Layer :

Function: Provides end-user services and interfaces directly with applications. It facilitates communication between software applications and lower layers.
Key Elements: Application protocols, interfaces.
Example: HTTP (Hypertext Transfer Protocol), FTP (File Transfer Protocol), SMTP (Simple Mail Transfer Protocol), DNS (Domain Name System).
Understanding Layer 7 (Application Layer)
Layer 7 is the top layer in the OSI model and is closest to the end-user. This layer interacts directly with software applications to provide communication functions. It's responsible for:

**Target Groups** :

`What is a target group ?`:

A target group is a logical grouping of resources (such as EC2 instances, IP addresses, or Lambda functions) that a load balancer can route traffic to. In AWS, target groups are used in conjunction with load balancers to define the backend resources that will receive traffic from the load balancer. Each target group has a specific protocol and port configuration, and it can be associated with one or more load balancers. The load balancer uses health checks to monitor the status of the targets in the group and routes traffic only to healthy targets. Target groups provide flexibility in managing and scaling your applications by allowing you to easily add or remove resources without affecting the overall architecture of your application.

Different Target Types we have in AWS ?: 

+ `Instance Target Type`: This target type allows you to register EC2 instances as targets for your load balancer. The load balancer will route traffic to the registered instances based on the specified protocol and port configuration.

+ `IP Target Type`: This target type allows you to register IP addresses as targets for your load balancer. This is useful when you want to route traffic to resources that are not EC2 instances, such as on-premises servers or containers running outside of AWS.

+ `Lambda Target Type`: This target type allows you to register AWS Lambda functions as targets for your load balancer. This is useful for serverless applications where you want to route traffic directly to Lambda functions without the need for EC2 instances.

+ `Application Load Balancer (ALB) Target Type`: This target type is specific to Application Load Balancers and allows you to register targets based on the application layer (Layer 7) routing rules. It supports routing based on URL paths, hostnames, and HTTP headers.


`Note` : You can add and remove instances from targets

**sticky session in loadbalancers**
`What is a sticky session ?`:

A sticky session, also known as `session affinity`, is a feature of load balancers that allows them to route a client's requests to the same backend server (EC2 instance) for the duration of a session (time). This is achieved by using `cookies or other mechanisms to track the client's session` and ensure that subsequent requests from the same client are directed to the same server. Sticky sessions can be beneficial for applications that require session persistence, such as e-commerce websites or applications that maintain user state. However, they can also lead to uneven load distribution if certain servers become overloaded with sticky sessions, so it's important to use this feature judiciously based on the specific requirements of your application.




**How Sticky Sessions Work**

+ *Session Identification*: The load balancer identifies and tracks client sessions, usually by using a session cookie, a URL parameter, or another method.

+ *Consistent Routing*: Once a client (end user or customer) is assigned to a backend server, subsequent requests from the same client are routed to the same server for the duration of the session.

+ *Session Data*: This is particularly useful for applications that store session data locally on the server. Without sticky sessions, the client’s requests might be distributed across different servers, which could lead to inconsistent experiences if session data is not shared or synchronized.


**Common Methods for Sticky Sessions**

+ *Cookie-Based Sticky Sessions*: The load balancer inserts a special cookie into the client’s browser. This cookie identifies the server to which the client is assigned. On subsequent requests, the client sends the cookie back to the load balancer, which uses it to route traffic to the same server.

+ *IP Hashing*: The load balancer uses the client’s IP address to determine which server to route the request to. This method is simpler but less flexible and can lead to issues if clients share IP addresses or change IPs frequently.

+ *URL Parameter*: A unique identifier is included in the URL of each request, and the load balancer uses this identifier to route the request to the appropriate server.


**WHY SHOULD WE USE STICKY SESSIONS IN LOADBALANCING ?**  

1. `Stateful Applications` (An application with a database): Ensures that clients interact with the same server throughout their session, which is essential for applications that maintain state or session-specific information on the server.

2. `Improved Performance` : Reduces the overhead of reloading session data from a shared store or database, which can improve application performance and responsiveness.

3. `Consistency`: Provides a consistent user experience by ensuring that all requests within a session are handled by the same server.

**AWS Load Balancer Routing Rules**
`What is a Load Balancer routing rule :`

A load balancer routing rule is a `set of conditions and actions` that determine how `incoming traffic` is directed to backend servers (targets) based on specific criteria. These rules allow you to configure the behavior of your load balancer to route traffic in a way that best suits your application's needs. For example, you can create routing rules that direct traffic based on URL paths, hostnames, HTTP headers, or query string parameters. This enables you to implement advanced routing strategies, such as directing requests for different parts of your application to different backend services or instances, improving performance and scalability.

A routing rule determines how the load balancer forwards traffic to target groups (EC2, ECS, Lambda, etc.).

**Types of Routing Rules**

+ Path-based routing 
+ Host-based routing 
+ Query string or http header 
+ http request method 
+ Sourceip 

1. `Host-based routing ( Host Header)`: 

This routing rule directs traffic based on the hostname specified in the HTTP request header. For example, you can route requests for `shop.example.com` to one target group and requests for `blog.example.com` to another target group.
This is useful when hosting multiple services or applications on the same load balancer but under different subdomains or hostnames. 

`Why it’s important`: Many companies want to run multiple apps on the same load balancer but separate them by domain.
and this can be cheaper . 



2. `Path Based Routing`:
This routing rule directs traffic based on the URL path of the incoming request. For example, you can route requests for `/api/*` to one target group and requests for `/user/*` to another target group. This allows you to route different types of requests to different backend services based on the structure of the URL.

This is particularly useful in microservices architectures where different services are exposed under different paths. For example:

Requests to /api might be routed to a target group running your API services.
Requests to /admin might be routed to a target group handling administrative functions.

`Why it’s important`: Lets you split a single domain into different backend services.

`Use case`: Microservices architecture where /login/* goes to an authentication service, /images/* goes to an image CDN (content delivery network) service, and /api/* goes to your backend API pods in EKS.

**HEALTH CHECKS IN LOAD BALANCERS**

This is way a load balancer checks your backend services to ensure that they are ready to receive traffic before it routes the traffic to them it uses the ping mechanism to check your backend servers in the (target groups) to make sure they are working properly before it routes traffic to it.

`Understanding Load balancers health checks`

`Health Check Configurations`

`Health Check protocol ;`
+ Health Checks are configured at the target group level within the load balancer
+ You can specify the protocol type e.g HTTP , HTTPS , TCP

+ `Health Check Path` : This is the specific endpoint path or url that your load balancer pings to determined weather the target (ec2 instance) server or application target is heathy and is able to handle or receive a request  e.g `/` : this is the default path and it uses the root (/) to test but you can set your own custom path e.g /health /healthcheck depending on configurations 


Advance settings 

+ `Health Check Port`:
This is the port number that your load balancer uses to perform health checks on the targets. It can be the same as the application port or a different port specifically designated for health checks. For example, if your application listens on port 80, you can configure the health check to use port 80 as well, or you can choose a different port (e.g., 8080) if you have a separate endpoint for health checks.
 
`Healthy Threshold` : 
The number of consecutive health checks successes required before considering an unhealthy target healthy.

`UnHealthy threshold`: This is the number of times your load balancer is going to ping your backend servers (targets) before it determines or mark the target as unhealthy .

`Timeout` : this is the period of time your load balancer will wait for a response before it marks the target as unhealthy


+ `Interval` : 
The approximate amount of time between health checks of an individual target
This is the time period between each health check ping. For example, if you set the interval to 30 seconds, the load balancer will ping the target every 30 seconds to check its health status.

+ `Success code `:

This is the HTTP status code that your load balancer expects to receive from the target in response to a health check ping. For example, if you set the success code to 200, the load balancer will consider the target healthy if it receives an HTTP 200 OK response from the target during a health check. 
other status codes 404,  405 issues 


**NOTE**: TCP does not use status codes instead it uses connection states : e.g 

+ `Open`: The load balancer successfully established a TCP connection to the target.
+ `Closed`: The load balancer attempted to establish a TCP connection but it was closed by the
target or did not respond within the timeout period.
+ `Error`: An error occurred while trying to establish a TCP connection to the target (e
.g., network issues, target not reachable).

**ROUTE 53** 

`What is Route 53`: ?

Amazon Route 53 is a scalable and highly available `Domain Name System (DNS)` web service provided by AWS. It is designed to route end-user requests to applications hosted on AWS or outside of AWS. Route 53 translates human-readable domain names (like www.example.com) into IP addresses that computers use to connect to each other. It also offers features such as `health checks, traffic routing policies, and domain registration, making it a comprehensive solution for managing DNS and directing traffic to your applications efficiently and reliably. 

Route 53 is an `AWS service` that you use to manage your DNS (Domain Name System) and you can use it for `DNS management , Traffic management ,domain registration , health checks and DNS security` . 

**Key Features of Route 53**

1. `DNS Management` : Route 53 allows you to manage your domain names and their associated DNS records, such as A records, CNAME records, MX records, and more. You can create and manage these records to route traffic to your applications hosted on AWS or elsewhere.

+ This allows you to perform DNS queries globally and manage domains on route 53
+ Supports public hosted zones (for internet-facing apps) and private hosted zones (for internal AWS networks).
+ Fully integrated with AWS resources like EC2, ALB, CloudFront, and S3 using Alias records (unique to AWS).

2. `Traffic Management` : Route 53 provides various traffic routing policies to help you manage how traffic is directed to your applications. These policies include:

+ `Simple routing`: Routes traffic to a single resource.
+ `Weighted routing`: Distributes traffic across multiple resources based on specified weights.
+ `Latency-based routing`: Routes traffic to the resource with the lowest latency for the user.
+ `Failover routing`: Routes traffic to a secondary resource if the primary resource is unhealthy.
+ `Geolocation routing`: Routes traffic based on the geographic location of the user.
+ `Geoproximity routing`: Routes traffic based on the geographic location of the user and the
resources, allowing for biasing towards certain resources.
+ `Multi-value answer routing`: Returns multiple healthy resources in response to DNS queries, allowing for client-side load balancing.

3. `Domain Registration` : Route 53 allows you to register new domain names directly through the AWS Management Console. You can search for available domain names, register them, and manage your domain settings all in one place.
+ When you register a domain ,Route 53 automatically creates a public hosted zone when you register a domain.
+ Supports top-level domains (TLDs) like .com, .net, .org, .ca, etc.
+ You can renew, transfer, or manage WHOIS contact info all inside the AWS Console.

4. `Health Checks` : Route 53 can monitor the health of your resources (like web servers or endpoints) using health checks. If a resource becomes unhealthy, Route 53 can automatically route traffic away from it to healthy resources based on your routing policies.
+ You can configure health checks to monitor endpoints, such as HTTP, HTTPS, or TCP.
+ Health checks can be associated with DNS records to enable failover routing.
+ You can set up CloudWatch alarms based on health check status for proactive monitoring.

5. `DNS Security` : Route 53 supports DNSSEC (Domain Name System Security Extensions) to help protect against DNS spoofing and ensure the integrity of your DNS data. With DNSSEC, you can digitally sign your DNS records, allowing clients to verify that the responses they receive are authentic and have not been tampered with.

**DNS RESOLUTIONS** 
DNS resolution is the process of translating a human-readable domain name (like www.google.com) into an IP address that computers use to identify each other on the network. When you enter a domain name into your web browser, the DNS resolution process begins, and it involves several steps:

1. The browser (Mozilla Firefox , Google Chrome ) checks its local cache to see if it has recently resolved (accessed) the domain name. If it finds a cached entry, it uses that IP address to connect to the server.

2. If the browser does not have a cached entry, it sends a DNS query (DNS request) to the configured DNS resolver (usually provided by your Internet Service Provider or a public DNS service like Google DNS or Cloudflare DNS).

3. The DNS resolver checks its own cache for the requested domain name. If it finds a cached entry, it returns the corresponding IP address to the browser.

4. If the DNS resolver does not have a cached entry, it starts a recursive query process to find the authoritative DNS server for the domain. It first queries the root DNS servers to find out which top-level domain (TLD) server is responsible for the requested domain.

5. The root DNS server responds with the IP address of the TLD DNS server (e.g., for .com domains).

6. The DNS resolver then queries the TLD DNS server to find out which authoritative DNS server is responsible for the second-level domain (e.g., team4techsolutions.com).

7. The TLD DNS server responds with the IP address of the authoritative DNS server for the requested domain.

8. The DNS resolver then queries the authoritative DNS server for the requested domain to get the IP address associated with the domain name.
